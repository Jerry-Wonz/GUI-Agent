# 实验与评测方案

## 1. 实验目标

本项目实验设计的核心目标不是追求绝对最强指标，而是建立一个完整、可复现、可分析的评测闭环。实验需要回答以下四个问题：

1. 系统是否具备基础 GUI grounding 能力
2. 系统是否能完成简化网页任务
3. 哪个模块是当前主要瓶颈
4. 轻量改进是否真的有效

## 2. 实验阶段划分

建议将实验拆成三个层次：

### 层次 A：Grounding 实验

只评估“文本到位置”的能力，不涉及多步 agent。

目标：
- 验证模型是否能找到页面目标元素

### 层次 B：单步 Action 实验

给定任务和当前页面，评估下一步动作预测是否合理。

目标：
- 验证策略模块是否学会基本操作

### 层次 C：任务级 Agent 实验

在网页环境中连续执行动作，评估任务是否完成。

目标：
- 验证系统是否具备完整 agent 能力

## 3. 推荐数据集与环境

## 3.1 GUI Grounding

### 首选：ScreenSpot

用途：
- 评估界面元素定位

优点：
- 任务边界清晰
- 适合先做 grounding baseline

输出目标：
- 预测点或框是否命中目标

### 可选：自建小规模网页截图集合

用途：
- 快速验证自己定义的网页场景

建议：
- 每类页面采 20 到 50 张截图
- 每张标注 1 到 5 个常见控件

适合早期调试，不适合作为唯一最终实验

## 3.2 Web Agent

### 首选：MiniWoB++

用途：
- 评估短程网页操作

优点：
- 环境可控
- 任务类型丰富
- 成功判定明确

适合任务：
- 点击按钮
- 填写文本
- 下拉选择
- 简单双击或滚动

### 进阶：Mind2Web 或其多模态版本

用途：
- 更接近真实网页任务

优点：
- 真实网页、多网站、多任务

缺点：
- 难度明显更高
- 工程复杂度更高

建议把它作为第二阶段扩展，而不是第一阶段主评测集

## 4. 指标设计

## 4.1 Grounding 指标

建议至少统计以下指标：

- `Point Accuracy`
  - 预测点击点是否落在目标框内
- `BBox IoU`
  - 若输出框，统计与标注框的 IoU
- `Top-k Hit`
  - 若输出多个候选区域，统计前 k 个候选中是否命中

建议主指标：
- `Point Accuracy`

## 4.2 Agent 指标

建议统计：

- `Success Rate`
  - 任务完成率
- `Average Steps`
  - 成功或全部任务的平均步数
- `Action Accuracy`
  - 单步动作类型是否正确
- `Grounding-assisted Click Accuracy`
  - 点击动作是否命中有效元素

建议主指标：
- `Success Rate`

## 4.3 过程指标

为了帮助分析失败原因，建议增加：

- grounding 平均置信度
- 每步动作延迟
- 每个任务的失败阶段
  - 感知失败
  - 定位失败
  - 决策失败
  - 执行失败

## 5. Baseline 设计

至少保留三类 baseline，这样实验结论会更稳。

## 5.1 Rule-based baseline

说明：
- 纯规则或模板方法

用途：
- 作为最低基线
- 验证环境和评测是否正常

示例：
- 根据关键词查 DOM
- 固定按钮位置点击

## 5.2 API-based VLM baseline

说明：
- 直接用多模态 API 预测下一步动作

用途：
- 快速建立强基线
- 低工程成本

优点：
- 上手快
- 便于分析提示词设计

缺点：
- 成本受 API 调用影响

## 5.3 Open-source small model baseline

说明：
- 使用 2B 到 7B 级开源模型

用途：
- 构建可复现方案
- 为后续微调打基础

建议：
- grounding 和 action 先分模块，不要一开始端到端

## 6. 关键实验设置

## 6.1 Grounding 实验

建议实验组：

1. 纯截图 grounding
2. 截图 + 文本 prompt 优化
3. 截图 + DOM 文本辅助
4. 候选区域重排序版本

想回答的问题：
- DOM 融合是否能改善定位
- 多候选排序是否能提高点击命中率

## 6.2 Agent 实验

建议实验组：

1. 端到端直接动作预测
2. `先 grounding 再 action` 两阶段方案
3. 带历史动作摘要
4. 带错误恢复机制

想回答的问题：
- 两阶段是否比端到端更稳定
- 历史信息是否真的有帮助
- 恢复机制是否能减少无效步数

## 6.3 消融实验

推荐至少做三组消融：

1. 去掉历史动作
2. 去掉 DOM 辅助
3. 去掉恢复机制

如果时间允许，再增加：

4. 不同候选数量 `top-1 / top-3 / top-5`
5. 不同最大步数限制

## 8. 错误分析框架

建议每次实验后都按以下类别记录失败案例：

### A. 感知错误

表现：
- 模型没看见目标元素
- 页面局部区域被忽略

### B. 定位错误

表现：
- 元素类型判断对了，但坐标偏了

### C. 决策错误

表现：
- 看到了元素，但选择了错误动作

### D. 执行错误

表现：
- 动作本身正确，但由于加载、焦点、滚动等问题失败

### E. 长程错误

表现：
- 前面步骤正确，后续因历史累积偏离目标

## 9. 推荐硬件与预算

### 最低实验配置

- CPU 开发环境
- 浏览器自动化
- 云端多模态 API

适合：
- 原型验证
- prompt baseline
- 小规模任务测试

### 推荐实验配置

- 单卡 GPU 16GB 至 24GB

适合：
- 小模型本地推理
- LoRA 微调
- grounding 模块单独训练

### 不建议的起步方案

- 一开始直接做端到端多卡训练
- 一开始就接真实复杂网站全流程

## 10. 预期结果区间

由于这是入门型实践项目，建议把目标分成三档。

### 基础完成

- grounding 任务可复现
- MiniWoB++ 若干子任务可以成功
- 有 baseline 对比和错误分析

### 较好完成

- grounding 与 agent 两条评测线都建立
- 至少一个改进项带来稳定提升
- 有比较清楚的模块瓶颈分析

### 优秀完成

- 在真实网页或 Mind2Web 类任务上完成扩展验证
- 改进项具有明确方法论价值
- 文档、代码、实验记录足够支撑论文初稿

## 11. 推荐实验顺序

建议按下面顺序做，效率最高：

1. Grounding baseline
2. MiniWoB++ 单步动作
3. 多步 agent loop
4. 错误分析
5. 加一个轻量改进
6. 做消融和汇总

这个顺序可以保证每一轮实验都在已有闭环上增量推进，而不是同时调太多变量。
