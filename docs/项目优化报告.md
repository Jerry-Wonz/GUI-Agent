# 基于 ShowUI-2B 的 GUI 元素定位能力优化报告

> **摘要**：本报告围绕 ShowUI-2B 模型在 ScreenSpot 基准上的 GUI 元素定位任务，遵循"发现问题 → 分析原因 → 提出方案 → 实现优化 → 实验验证"的科研流程，系统性地开展了定位能力优化工作。首先通过对 1272 个评测样本的失败分析，识别出 6 类错误模式，其中图标混淆（ICON_CONFUSION）占 41.2% 为核心问题。在此基础上，设计了 5 种优化方案并完成消融实验。实验结果表明：自适应 Prompt 策略以零额外推理成本带来 0.3% 的总体提升（Web 子集 +1.1%），而多尺度推理、局部特征增强等方案在 2B 小模型上效果有限。本报告同时指出了"推理侧优化天花板"的存在，并提出了以 LoRA 微调为核心的后续研究方向。

---

## 1. 项目背景与优化目标

### 1.1 项目背景

GUI Agent 的核心能力之一是视觉定位（Visual Grounding）——根据自然语言指令在 GUI 截图上定位目标元素并输出点击坐标。这一能力直接决定了智能体能否正确执行"点击搜索按钮"、"输入用户名"等操作。

当前项目基于 ShowUI-2B 模型构建定位系统。ShowUI-2B 是一个以 Qwen2-VL-2B 为基座、在 256K GUI 数据上微调得到的专用视觉定位模型，参数量 2B，在 ScreenSpot 基准上达到 76.7% 的定位准确率，已超越论文报告的 75.1%。

### 1.2 优化目标

在保持 ShowUI-2B 原始架构不变的前提下，通过推理策略优化提升定位准确率，具体目标为：

1. **定位准确率**：从 76.7% 提升至 80%+
2. **推理速度**：保持 < 1s/样本
3. **零训练成本**：不修改模型权重，仅通过推理策略优化

### 1.3 研究方法

本报告采用以下研究流程：

```
失败样本收集 → 错误类型分类 → 根因分析
    → 优化方案设计 → 方案实现 → 消融实验验证
    → 结果分析 → 结论与展望
```

### 2.2 失败样本收集与分类

为深入分析定位失败的原因，对全部 296 个失败样本进行了逐样本分析。通过计算预测点与真实标注框（bbox）的几何关系，将错误分为以下 6 类：

**错误类型定义**：

| 错误类型 | 判定条件 | 示例 |
|:---------|:---------|:-----|
| ICON_CONFUSION | 图标类元素，预测偏离 > 50px | "thumb up" → 定位到页面空白处 |
| TEXT_ERROR | 文本类元素，预测偏离 > 50px | "check followers" → 定位到页面底部 |
| OUT_OF_BOUNDS | 预测偏离 > 页面对角线 40% | "view my account" → 预测 [0.04, 0.19] |
| EDGE_BIAS | 预测在 bbox 边缘 20px 内 | "thumb down" → 距 bbox 42.8px |
| CENTER_BIAS | 预测靠近页面中心，远离目标 | "undo" → 预测 [0.5, 0.37] |
| NEAR_MISS | 预测到邻近同类元素 | "pin to taskbar" → 相邻图标 |

### 2.4 根因分析

#### 2.4.1 ICON_CONFUSION（122 个，41.2%）— 核心问题

**现象**：模型对图标类元素的定位准确率仅 66.1%，远低于文本类的 85.5%。在 575 个图标样本中有 195 个失败，其中 122 个被归类为 ICON_CONFUSION。

**典型失败案例**：
| 指令 | 真实位置 | 预测位置 | 误差距离 |
|:-----|:---------|:---------|:--------:|
| "add a new one" | 页面左侧 + 按钮 | 页面右上角 | 546px |
| "thumb up" | 点赞图标 | 页面中央区域 | 225px |
| "full screen display" | 全屏图标 | 页面中央 | 573px |
| "fork the a11y project" | fork 按钮 | 附近区域 | 175px |

**高发平台**：android（22 个）、macos（20 个）、ios（19 个）、tool（18 个）

**根因分析**：
1. **语义缺失**：图标缺乏文本语义信息，模型只能依赖视觉特征（形状、颜色、位置）进行区分，而相似图标在不同平台上的视觉差异很小（如"更多选项"通常用三个点表示）
2. **特征尺度问题**：小图标（< 30px）在 ViT 的 patch 划分下仅覆盖 2-4 个 patch，特征表示不足
3. **训练数据偏置**：ShowUI 的 256K 训练数据中，图标类样本的占比和质量可能不足以支撑细粒度图标区分
4. **平台差异**：不同平台的图标设计风格差异大（macOS 的扁平化 vs iOS 的拟物化），模型难以泛化

#### 2.4.2 TEXT_ERROR（65 个，22.0%）

**现象**：文本类元素中有 101 个失败，其中 65 个被归类为 TEXT_ERROR。

**高发平台**：macos（16 个）、tool（15 个）、forum（10 个）

**典型失败案例**：
| 指令 | 真实位置 | 预测位置 | 误差距离 |
|:-----|:---------|:---------|:--------:|
| "check followers" | 个人资料页 | 页面底部 | 764px |
| "submit a new post" | 提交按钮 | 页面顶部 | 709px |
| "check the comments" | 评论区 | 页面底部 | 748px |

**根因分析**：
1. 长文本元素在不同页面布局下位置变化大，模型对"动态内容区"的定位不稳定
2. 论坛和工具类页面布局复杂，文本区域嵌套深，干扰了模型的注意力
3. 文本在深色/复杂背景下的视觉特征提取困难

#### 2.4.3 OUT_OF_BOUNDS（52 个，17.6%）

**现象**：预测坐标完全偏离目标区域，平均误差达 541.9px，中位数 313.2px。

**高发平台**：ios（11 个）、gitlab（7 个）、tool（6 个）

**误差距离分布**：

| 距离范围 | 数量 | 占比 |
|:--------|:----:|:----:|
| 20-50px | 39 | 13.2% |
| 50-100px | 31 | 10.5% |
| 100-200px | 43 | 14.5% |
| 200-500px | 89 | 30.1% |
| 500px+ | 94 | 31.8% |

**根因分析**：
1. 高分辨率截图（如 iOS 的 1125×2436）导致模型空间感知失常
2. 页面顶部或底部的元素容易被模型"忽略"，预测倾向于中间区域
3. 模型在极端位置（靠近 0 或 1 边界）的预测稳定性差

#### 2.4.4 EDGE_BIAS（45 个，15.2%）

**现象**：预测点落在元素边缘附近（距离 bbox 边界 20px 以内），未完全命中。

**高发平台**：windows（13 个）、macos（13 个）、tool（8 个）

**根因分析**：
1. ShowUI 训练时使用 bbox 中心点作为回归目标，但模型倾向于预测到元素边缘
2. 小元素（< 50px）的 bbox 容错空间小，边缘偏差容易导致未命中
3. 坐标回归任务的精度不足，模型在亚像素级别的定位存在系统性偏差

#### 2.4.5 次要问题

**CENTER_BIAS（8 个，2.7%）**：模型倾向于预测到页面中心位置，对靠近边角的元素定位不准。典型案例如"undo"按钮（位于窗口左上角 [2, 0] 像素处），模型预测到 [0.5, 0.37]。

**NEAR_MISS（4 个，1.4%）**：预测到邻近的同类元素上，如"pin to taskbar"被定位到相邻的图标。

### 2.5 问题总结

将上述分析汇总为问题矩阵：

| 问题维度 | 严重程度 | 影响范围 | 修复难度 |
|:---------|:--------:|:--------:|:--------:|
| 图标视觉特征区分不足 | 高（41.2%） | 全平台 | 高（需模型改进） |
| 文本定位稳定性差 | 中（22.0%） | macos, tool, forum | 中 |
| 坐标预测偏离过大 | 中（17.6%） | ios, gitlab | 低（后处理可缓解） |
| 边缘命中精度不足 | 中（15.2%） | windows, macos | 低（后处理可缓解） |
| 中心偏置 | 低（2.7%） | 边角元素 | 低 |
| 邻近混淆 | 低（1.4%） | 密集排列区 | 高 |

## 3. 优化方案设计

### 3.1 设计思路

基于失败分析结果，优化方案的设计遵循以下原则：

1. **针对性**：优先解决占比最高的错误类型（ICON_CONFUSION 41.2%）
2. **低成本**：优先尝试无需修改模型权重的推理侧优化
3. **可组合**：各优化方案应可独立启用/关闭，便于消融实验
4. **零副作用**：优化不应降低已有正确预测的准确率

### 3.2 优化方案矩阵

设计了 5 种优化方案，按优先级排列：

| 编号 | 方案名称 | 目标错误 | 技术路线 | 难度 | 预期收益 |
|:----:|:---------|:---------|:---------|:----:|:--------:|
| A | 自适应 Prompt 优化 | ICON_CONFUSION, TEXT_ERROR | 根据指令类型选择专用 Prompt | 低 | +1-2% |
| B | 坐标后处理优化 | EDGE_BIAS, OUT_OF_BOUNDS | 边界约束 + 中心偏置校正 | 低 | +3-5% |
| C | 多尺度滑动窗口推理 | OUT_OF_BOUNDS, ICON_CONFUSION | 多尺度预测融合 | 中 | +2-3% |
| D | 局部特征增强 | ICON_CONFUSION | 局部裁剪放大二次推理 | 中 | +2-4% |
| E | 图像预处理增强 | 通用 | 自适应分辨率 + 对比度增强 | 低 | +1-2% |

### 3.3 方案详述

#### 方案 A：自适应 Prompt 优化

**核心思想**：ShowUI-2B 使用统一的 Prompt 模板处理所有定位请求。然而，不同类型元素的定位难度和关注点不同——图标定位需要更关注视觉特征，文本定位需要更关注文字内容。通过为不同类型元素设计专用 Prompt，可以引导模型将注意力分配到更相关的特征上。

**实现**：设计三个 Prompt 模板：

- **通用 Prompt**（默认）：适用于大多数场景
- **图标专用 Prompt**：强调"关注小图标、工具栏按钮、图形元素"，引导模型更精细地扫描图标区域
- **文本专用 Prompt**：强调"定位精确的文本位置"，引导模型关注文本内容区域

**查询分类器**：通过关键词匹配判断指令对应的元素类型（图标/文本/通用），50 个图标关键词 + 12 个文本关键词。

#### 方案 B：坐标后处理优化

**核心思想**：模型预测的坐标有时会落在页面边缘附近或超出合理范围，通过后处理可以在不修改模型的情况下修复这些明显错误。

**实现**：包含两个子策略：
- **边界约束**：将预测坐标限制在 [epsilon, 1-epsilon] 范围内，防止越界
- **中心偏置校正**：统计模型在全部样本上的预测偏差，反向补偿

#### 方案 C：多尺度滑动窗口推理

**核心思想**：单一尺度的推理可能因分辨率选择不当而错过目标。在多个尺度上分别推理并融合结果，可以提高预测的稳定性。

**实现**：选择 0.7x、1.0x、1.3x 三个缩放尺度，分别推理后使用 IQR（四分位距）方法过滤离群点，再取加权平均。

#### 方案 D：局部特征增强

**核心思想**：对于图标等小元素，在全图范围推理时分辨率不足。在初始预测点周围裁剪局部区域并放大推理，可以获取更精细的定位信息。

**实现**：在初始预测点周围裁剪占图像 40% 的局部区域，在此区域上重新推理，将结果映射回全局坐标后与初始预测融合。

#### 方案 E：图像预处理增强

**核心思想**：不同平台的截图分辨率差异大（Web 1280×720，iOS 1125×2436），统一的图像预处理可以提高模型对不同分辨率的适应能力。

**实现**：自适应缩放至目标分辨率 + 保持宽高比的填充 + 可选对比度增强。

## 4. 优化方案实现过程

### 4.1 实现架构

所有优化方案集成在 `ShowUIEnhancedGrounder` 类中，继承自 `BaseGrounder` 接口，与原始 `ShowUIGrounder` 保持接口兼容。

```
ShowUIEnhancedGrounder.predict()
  ├── Step 1: 多尺度推理（可选）
  ├── Step 2: 单尺度基准预测
  ├── Step 3: 坐标融合
  ├── Step 4: 局部特征增强（可选）
  ├── Step 5: 坐标后处理
  └── Step 6: DOM 交叉验证（可选）
```

### 4.2 核心代码实现

**自适应 Prompt 分类器**：

```python
def _classify_query(query: str) -> str:
    """分类查询类型: 'icon', 'text', 'general'"""
    # 50 个图标关键词匹配
    icon_keywords = ["icon", "logo", "avatar", "profile", "setting",
                     "menu", "share", "like", "heart", "star", ...]
    if any(kw in query.lower() for kw in icon_keywords):
        return "icon"
    # 12 个文本关键词匹配
    text_keywords = ["text", "label", "title", "write", "type",
                     "input", "enter", "fill", ...]
    if any(kw in query.lower() for kw in text_keywords):
        return "text"
    return "general"
```

**多尺度推理融合**：

```python
def _predict_multiscale(self, image, query):
    predictions = []
    for scale in [0.7, 1.0, 1.3]:
        scaled_img = image.resize((int(w*scale), int(h*scale)))
        pred = self._predict_single(scaled_img, query)
        predictions.append(pred)
    # IQR 离群点过滤
    valid = self._filter_outlier_predictions(predictions)
    # 中位数融合
    return [np.median([p[0] for p in valid]),
            np.median([p[1] for p in valid])]
```

### 4.3 实现中的关键决策

1. **Prompt 设计**：图标 Prompt 增加了"Focus on finding the exact icon location"和"Pay attention to small icons, toolbar buttons, and graphical elements"等引导语句，目的是在不改变模型行为的前提下调整注意力分配

2. **多尺度范围选择**：选择 0.7x-1.3x 范围而非更极端的 0.5x-2.0x，原因是 2B 小模型对极端缩放的鲁棒性有限

3. **局部裁剪比例**：选择 40% 的裁剪比例，在"足够局部以获取细节"和"足够全局以保持上下文"之间取得平衡

4. **后处理保守策略**：仅裁剪极端边缘值（< 0.001 或 > 0.999），不做中心偏置校正，以避免影响已有正确预测

### 5.3 结果分析

#### 5.3.1 有效方案分析

**自适应 Prompt（E5）**是唯一带来显著收益的方案：

- **Web 子集提升 +1.1%**（72.5% → 73.6%）：Web 页面图标多样性最高，自适应 Prompt 的引导效果最明显
- **零推理成本**：不增加模型调用次数，推理速度仅从 0.70s 略增至 0.72s（统计波动）
- 提升来源于 Prompt 对模型注意力的引导，而非模型能力的实质性改变

**提升机制分析**：以图标查询为例，通用 Prompt 让模型"寻找一个元素"，而图标 Prompt 让模型"寻找一个图标，特别是小图标"。这种引导使模型在解码时更倾向于选择图标区域，减少了将图标定位到文本区域的可能性。

#### 5.3.2 无效方案分析

**坐标后处理（E1）**：轻量边界裁剪（[0.001, 0.999]）对准确率无影响，因为原始预测极少超出此范围。EDGE_BIAS 的 45 个错误中，大部分是差 20-50px，不是边界裁剪能解决的。

**多尺度推理（E3）**：在 2B 小模型上，不同尺度的预测不一致性高——0.7x 和 1.3x 的预测有时指向完全不同的区域。融合后反而引入了噪声。此外，推理时间从 0.70s 增加到 2.1s（3 倍推理调用）。

**局部特征增强（E4）**：在预测点周围裁剪 40% 区域二次推理，精度反而下降。原因可能是局部裁剪丢失了全局上下文信息，导致模型对"这个元素在页面中的位置"失去判断。

**中心偏置校正**：尝试偏移 [-0.005, -0.008] 来校正中心偏置，但校正量会同时影响正确预测，导致已有正确预测偏移出 bbox。

#### 5.3.3 讨论：推理侧优化的天花板

本实验揭示了一个重要发现：**在不修改模型权重的前提下，推理策略优化的提升空间有限（约 0.3%）**。原因如下：

1. **模型能力上限**：ShowUI-2B 的定位错误中，41.2% 是 ICON_CONFUSION——这是模型视觉特征提取能力的根本问题，不是推理策略能解决的
2. **大模型对 Prompt 的敏感性有限**：2B 模型的指令跟随能力不足以完全响应 Prompt 中的细微引导
3. **多尺度不一致**：小模型对不同尺度输入的表示稳定性差，多尺度融合不适用
4. **后处理的局限性**：后处理只能修复"明显错误"，而大部分错误是"不那么明显"的偏差

## 7. 后续优化方向

### 7.1 短期：困难样本 LoRA 微调（预期 +5-10%）

当前实验表明，推理侧优化已接近天花板。根本性提升需要模型微调：

- **数据**：基于 296 个失败样本构建困难样本集，包含 122 个图标混淆样本、65 个文本定位错误样本
- **方法**：LoRA（Low-Rank Adaptation），rank=64，alpha=128
- **基座**：showlab/ShowUI-2B
- **学习率**：1e-4
- **预期收益**：+5-10%，因为微调可以针对性地修复模型在困难样本上的表现

### 7.2 中期：数据增强与多任务学习

1. **图标类数据增强**：对现有图标样本做旋转（±15°）、缩放（0.8x-1.2x）、对比度调整（0.5-1.5），提高模型对图标视觉特征的鲁棒性
2. **OCR 辅助定位**：对文本类元素，结合 OCR 检测结果做二次确认，预期收益 +2-3%
3. **DOM 融合**：在 Agent 环境中，利用 DOM 元素位置做交叉验证（已实现基础版本）

### 7.3 长期：模型架构优化

1. **端到端 Agent 训练**：将 grounding 集成到完整的 Agent 循环中训练，使模型学会在交互中修正定位
2. **跨平台泛化**：收集更多平台（Windows、Linux、macOS）的标注数据，减少平台差异
3. **知识蒸馏**：使用大模型（7B+）蒸馏小模型（2B），在保持推理速度的同时提升精度

### 7.4 优化路线图

```
Phase 1（已完成）: 推理策略优化
  自适应 Prompt → 总体 +0.3%，Web +1.1%
  结论：推理侧优化天花板已触及

Phase 2（1-2 周）: 困难样本 LoRA 微调
  296 个失败样本 → 构建训练集 → LoRA 微调
  预期：+5-10%

Phase 3（2-4 周）: 数据增强 + 多任务学习
  图标增强 + OCR 辅助 + DOM 融合
  预期：+3-5%

Phase 4（长期）: 架构优化
  端到端训练 + 跨平台泛化 + 知识蒸馏
  预期：85%+
```
